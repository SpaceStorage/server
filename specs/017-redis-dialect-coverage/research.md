# Research: Complete-Product Redis Dialect Coverage

**Feature**: `017-redis-dialect-coverage` | **Date**: 2026-11-26

Each item resolves a Technical Context unknown or a technology choice. Format: Decision / Rationale / Alternatives considered. Inputs: [spec.md](spec.md) (clarify 2026-10-31 and 2026-11-26), constitution 1.3.0, sibling plans `002` (Redis handler, credential-bound namespace, `SS.*`), `003` (L0–L4 inventory, extension path, `hyperloglog` already listed), `005` (IR, isolation), `006` (leadership lease), `008` (stats), `013` (WAL, TTL job), `015` (matrix, FR-016), `016` (first-binary Redis subset).

No `[NEEDS CLARIFICATION]` remains in the spec. The decisions below close planning choices the spec left to this phase (how a command becomes a type operation, where the table lives, how blocking and pub/sub sit on the runtime).

## R1. Capability table lives in `compat`, consulted before IR

- **Decision**: The complete-product Redis command/option table is data in `crates/compat` (`classify_redis`). `DialectProfile::CompleteProduct` returns `Must` for every command in [contracts/capability-table.md](contracts/capability-table.md) and `MustNot` for the not-supported list. `FirstBinary` and `HandlersComplete` keep today's string list (`AUTH`, `PING`, `GET`, `SET`, `DEL`, `EXISTS`, `SCAN`, `SELECT`, `TTL`, `PTTL`, `EXPIRE`). The handler calls `classify_outcome` **before** building a `LogicalRequest`, as it already does. A `MustNot` becomes `-ERR unknown command '<name>'` (the `002` Redis not-supported form) with no IR and no write.
- **Rationale**: Spec FR-001, FR-011, FR-012, FR-015. `015` FR-016 already says this feature owns the complete-product surface and the merged matrix points here. One table stops `handler-redis` and `compat` from drifting. The current `classify_redis` ignores the profile (`let _ = profile`); that is the bug this feature fixes, not a behavior to preserve on the complete product.
- **Alternatives considered**: A private match table inside `handler-redis` (rejected: `015` handlers must share one classify); generating the table from this markdown at build (fragile, and `016` conformance could not pin it); flipping every profile at once (rejected: `016` SC-006 requires `HGET` to error on the first binary).

## R2. One default key-space container; typed entries, not typed containers

- **Decision**: Each namespace has one Redis key-space container, addressed by the existing `protocols.redis.default_container` (default name `redis`, schema `public`). Its store type stays L2 `kv_collection` so the `002` canonical path (`SS.GET` / `SS.PUT` / `SS.SCAN`) and other protocols see **one** object. Every Redis key is an entry in that container. The entry carries exactly one `RedisVisibleType`: `string`, `hash`, `list`, `set`, `zset`, `stream`. The first write command creates the entry and sets the type. A later command for a different type returns `-WRONGTYPE Operation against a key holding the wrong kind of value` and writes nothing. `TYPE` reports that name. HyperLogLog and bitmap keys report `string` (FR-004, FR-017) because that is the Redis-visible type; the payload kind inside the entry is `hyperloglog` or `bitmap`.
- **Rationale**: Clarification 2026-10-31 Q3 and FR-003. A container-per-key would explode the catalog and break "one shared store object". A container-per-type (six containers) would make `SCAN`/`DBSIZE` a cross-container union and hide the object from other protocols. Putting the type on the entry keeps `WRONGTYPE` local and keeps `002`'s container mapping.
- **Alternatives considered**: One L3 `kv_store` per Redis type (rejected: six objects, `SCAN` lies); encoding the type only in a key prefix (rejected: `TYPE` could drift from the payload); reusing the first-binary raw string blob for every type (rejected: lists and streams are not strings, and `WRONGTYPE` would be unenforceable).

## R3. Commands lower to `TypeOp` on the shared interface

- **Decision**: `handler-redis` parses RESP2, checks arity and the capability table, then submits one `LogicalRequest` to `005`. Point strings stay `Point` / `Object` / `Mutate` as the first binary does. Collection, bitmap, HLL, and stream commands are `TypeOp` (or `Mutate` with an op name) whose op is the store operation, not the Redis command spelling: `hash.put`, `list.push_front`, `set.add`, `zset.add`, `stream.append`, `bitmap.set`, `hyperloglog.add`, and so on. Reply rendering (bulk, integer, nested array, error) stays in the handler. The handler crate still depends only on `protocol-core`, `types`, `query`, `auth`/`authz`, and `compat` — not on the `types` L0 primitive module, `storage`, or `crypto`.
- **Rationale**: Constitution IV and architectural contract; `002` FR-035; `003` FR-040. Redis command names are a wire dialect. The type system already has the types and operations ([`003` type-inventory](../003-type-system/contracts/type-inventory.md)): L0 `hash_table` (hash, and the value-less set payload), L0 `linked_list`/`deque` (list), L0 `skip_list` + L0 `hash_table` (zset index + member map), L0 `ring_buffer` + L0 `append_segment` (stream append-log), L0 `bitmap` (bitmap family), and the registered extension L0 `hyperloglog`.
- **Alternatives considered**: A Redis-shaped engine crate that owns its own maps (rejected: protocol-private type system); expanding `LogicalRequest` with a `RedisCommand` variant (rejected: that leaks one protocol into the IR `005` says is canonical); shelling out to a stock `redis-server` (rejected: Principle III, and it would not be the shared store).

## R4. HyperLogLog is the registered L0 primitive, Redis type `string`

- **Decision**: Implement `hyperloglog` in `crates/types/src/l0.rs` and register it from `crates/types/src/catalog.rs` + `crates/types/src/descriptor.rs` with the descriptor `003` already published under Registered extensions: level L0, kind data structure, creatable, modes memory (default) / persistent / hybrid, schema optional `precision` default 14 (`2^14` registers), ops `add`, `count`, `merge`, `clear`, standard error `1.04/√m` ≈ 0.81% at the default. `PFADD` → `add`, `PFCOUNT` → `count` (sparse inputs merge for the estimate), `PFMERGE` → `merge` into the destination key, creating it as an HLL `string` if missing. Canonical form is the `003` versioned payload for this type. No Redis command reads or writes a dense string encoding of the registers.
- **Rationale**: Spec FR-017; clarification 2026-11-26; `003` FR-045–FR-049 and FR-046 (baseline descriptors and the count 55 do not change). The Redis `TYPE` of an HLL key is `string` because stock clients treat `PF*` keys as strings; the store type is still `hyperloglog`.
- **Alternatives considered**: A private 12 KiB string blob inside the handler (rejected: protocol-private encoding, and PostgreSQL could not run `count`); using `bloom_filter` (rejected: different op set and error model); a new L2 abstraction (rejected: the spec places it at L0 beside `Bloom Filter`).

## R5. Bitmaps ride L0 `bitmap`, still Redis type `string`

- **Decision**: `SETBIT`, `GETBIT`, `BITCOUNT`, `BITPOS`, and `BITOP` (`AND`/`OR`/`XOR`/`NOT`) map onto the registered `003` L0 `bitmap` operation set — `set`, `test`, `cardinality` (over a range), `rank`/`select`, and `and`/`or`/`xor`/`not` (exact operation names per [`003` type-inventory](../003-type-system/contracts/type-inventory.md)). Missing bits read as 0. `BITOP` writes a destination key of Redis type `string` whose payload kind is `bitmap`, length per Redis (longest input, or the `NOT` source length). Offset past `015` `limits.max_value` rejects as a limit error before the op. `TYPE` reports `string`.
- **Rationale**: Spec User Story 5 and the assumption "bitmap family rides on the existing `Bitmap / Bitset` primitive". `003` `bitmap` already has these ops. Reporting `string` matches stock Redis, which has no separate bitmap type.
- **Alternatives considered**: Bit operations on a raw string in the handler (rejected: private encoding, and `BITOP` would fork integer semantics); reporting `TYPE` as something other than `string` (rejected: FR-004 lossless mapping to the Redis-visible name).

## R6. Stream order is a per-key mode; total order uses a leadership lease

- **Decision**: A stream entry records `order: Total | Producer`, chosen when the key is created. Implicit `XADD` and `XGROUP CREATE` on a missing key use `Total`. `Producer` is selected only by the documented create option on that first write (a container option surfaced as `XADD` creation-time option documented in [contracts/redis-mappings.md](contracts/redis-mappings.md) under "Stream Mapping Details → Ordering Modes", not a new Redis command). Total-order appends call `006` `LeadershipLease` for the **stream key** (epoch per key, not per container): the append carries `epoch == current`; a stale epoch returns an error and is not an entry. IDs are the Redis millisecond-sequence pair; `*` allocates a strictly increasing ID; an explicit ID ≤ last ID is rejected. Producer order keeps each producer's ID sequence and does not take a lease; observers may see interleaving. Group offsets and the PEL are defined against whichever order the key has. `XAUTOCLAIM` is `MustNot`.
- **Rationale**: Clarification 2026-10-31 Q2; constitution XII ("a datatype that needs a single writer or a total order MUST request leadership from the control plane; it MUST NOT assume the datatype-level primary serializes every write"); `006` FR-006 (epoch fence, not a wall-clock fence). One lease per stream key, not one Raft group per key: the namespace group grants the lease, which is the `006` model.
- **Alternatives considered**: A process-local mutex (rejected: lies across nodes and skips the epoch fence); making the whole key-space container single-writer (rejected: strings and hashes are leaderless); Redis Cluster slot ownership (rejected: `CLUSTER` is not-supported and would be a second topology).

## R7. Blocking parks one connection task

- **Decision**: `BLPOP`, `BRPOP`, `BZPOPMIN`, `BZPOPMAX`, and `XREAD BLOCK` register a waiter on the target key and `.await` a `tokio::sync::Notify` (or oneshot) on that connection's task. Timeout is the client timeout, except timeout `0` means "no client deadline". If `protocols.redis.max_block` is set, the effective deadline is `min(client, max_block)` and `0` becomes `max_block`. Unset `max_block` preserves stock indefinite blocking. On fire, timeout, disconnect, or server drain the waiter is removed and the connection accepts commands again. The wait is not `spawn_blocking` and not a worker sleep. Other connections are unaffected. Pipelined commands on the same connection stay queued behind the blocked command (stock Redis connection rules).
- **Rationale**: Spec FR-006 and clarification 2026-10-31 Q1. Principle II: database request work must not block worker threads. A parked Tokio task is the same pattern `005` already uses for subscribe-wait.
- **Alternatives considered**: A dedicated blocking thread pool (rejected: fights Principle II and caps concurrency at pool size); rejecting timeout `0` always (rejected: clarify says stock semantics are the default); blocking inside `EXEC` (rejected: Redis forbids blocking commands in `MULTI` — those are queuing errors, see R8).

## R8. Transactions are a connection batch with Redis no-rollback

- **Decision**: `MULTI` moves the connection to `TxnState::Queuing`. Queued commands are stored as already-lowered `LogicalRequest`s plus their render plan. `DISCARD` drops the queue. `EXEC` runs the queue in order on that connection as one `005` session batch under the documented default isolation (`READ COMMITTED`, `015`/`005` — Redis has no isolation field). A command that fails at execution (for example `WRONGTYPE`) contributes an error reply **inline**; earlier writes stay; later commands still run. A queuing-time syntax or arity error flags the transaction dirty; `EXEC` then returns the Redis `EXECABORT` error and runs nothing. `WATCH` records keys and a version token taken from the entry's durable/logical version; any other session's write or expiry of a watched key before `EXEC` makes `EXEC` return the Redis null bulk and run nothing. `UNWATCH` and a finished `EXEC` clear the set. Blocking commands inside `MULTI` are a queuing error. Isolation is not upgraded to `SNAPSHOT` or `SERIALIZABLE`.
- **Rationale**: Spec FR-008 and User Story 3. Redis `EXEC` is explicitly not rollback. Mapping it onto a SQL transaction that rolls back would break SC-004. `WATCH` is optimistic concurrency on the shared store, which fits a version check better than a lease. `SERIALIZABLE` is a product non-goal (`015`).
- **Alternatives considered**: `005` `TxnBegin`/`TxnCommit` with rollback (rejected: contradicts Redis no-rollback); ignoring `WATCH` (rejected: scenario 3); holding a leadership lease for every `MULTI` (rejected: strings are leaderless, and a lease would not abort on a concurrent write the way `WATCH` must).

## R9. Pub/sub is an in-process, namespace-scoped bus

- **Decision**: `crates/node` holds a `PubSubBus` keyed by namespace id. `SUBSCRIBE` / `PSUBSCRIBE` attach the connection; the connection enters subscribe mode and its replies match Redis (including `PING` → the subscribe-mode array). `PUBLISH` delivers to subscribers of that channel and to matching patterns **in the same namespace only**, on this process, and returns the local receiver count. Messages are not WAL records, not Raft records, and not replayed after restart. Unsubscribe-all leaves subscribe mode. A publish in namespace A is invisible to namespace B even on the same node.
- **Rationale**: Spec FR-009 and FR-016. Stock Redis pub/sub is fire-and-forget. Cross-node fan-out would be a new replication stream this spec does not require; the conformance suite is multi-connection on one node. Documenting "this process" keeps a later cluster fan-out from pretending to be durable.
- **Alternatives considered**: WAL-backed pub/sub (rejected: FR-016 forbids replay); using Streams as the pub/sub implementation (rejected: different ack and retention semantics); a cluster-wide broadcast in this feature (rejected: not in the spec, and it would couple the dialect to `012` gossip).

## R10. `INFO` maps product stats; missing fields are omitted

- **Decision**: `INFO` with no argument and `INFO <section>` emit Redis CRLF `# section` blocks for `server`, `clients`, `memory`, `stats`, `keyspace`, `replication`, plus `commandstats` when counters exist. Values are read from `008` / node stats for this process and this namespace: `keyspace` and `DBSIZE` count live non-expired keys of the key-space container; `stats` counters move when commands do; `replication` reports this node's real role (`master` only when this node is serving the key-space as a coordinator with no Redis-replica link — SpaceStorage is not Redis replication, so `connected_slaves:0` and a documented `role` from membership, never a hardcoded `role:master` on a follower that is not one). `redis_version` is the dialect baseline `7.4.0-spacestorage`. Fields with no internal equivalent (`mem_fragmentation_ratio`, `aof_enabled`, …) are omitted, not filled with stock constants. `OBJECT` is the documented subset `ENCODING` and `IDLETIME` only; other subcommands are not-supported.
- **Rationale**: Spec FR-010 and User Story 4. Constitution X: do not invent a second statistics store. Monitoring must be able to join `INFO` to Prometheus, which means the numbers are the product's numbers.
- **Alternatives considered**: A full stock Redis `INFO` template with zeros (rejected: "never constant fakes"); skipping `INFO` until `008` grows Redis-shaped series (rejected: the mapping is the feature).

## R11. Not-supported list is closed and named

- **Decision**: The complete closed list is [contracts/not-supported.md](contracts/not-supported.md) (canonical — do not restate it elsewhere). Its members are always `MustNot`, on every profile including complete product, grouped by family: geospatial (incl. the `_RO` aliases and `GEOSEARCHSTORE`), `XAUTOCLAIM`, Lua/scripting (`EVAL`/`EVALSHA`, `SCRIPT`), Functions (`FCALL`/`FCALL_RO`, `FUNCTION`), Modules, Cluster, Sentinel, ACL management (`AUTH` stays MUST), historical/deprecated replication and admin verbs (`MIGRATE`, `REPLICAOF`, `SLAVEOF`, `SYNC`, `PSYNC`, `DEBUG`, `RESTORE`, `DUMP`, `RENAME`, …), and RESP3-only features. Unknown commands and unknown options of a listed command take the same path. Error text is `-ERR unknown command '<COMMAND>'` or `-ERR unknown subcommand or wrong number of arguments` for a bad subcommand, matching the `002` renderer. No `+OK`, no empty array that means success.
- **Rationale**: Spec FR-012; clarification 2026-11-26; `015` matrix Redis row. Listing them in `compat` makes SC-002 a table walk, not a hunt through the handler.
- **Alternatives considered**: Implementing geo on `003` `spatial_index` (rejected: user exclusion below the 7.4 baseline); returning a Redis `nil` for unknown commands (rejected: silent empty success).

## R12. Key and hash-field expiry share the `013` TTL job

- **Decision**: A key expiry is a deadline on the entry, stored with the entry and indexed for `013` `TTL expiration`. When the deadline passes, the job writes a tombstone/delete for that key; readers treat a past deadline as missing even before the job runs (`purge-on-read`, which the first-binary handler already does for strings). Hash-field expiry (`HEXPIRE`, `HPEXPIRE`, `HEXPIREAT`, `HPEXPIREAT`, `HTTL`, `HPTTL`, `HEXPIRETIME`, `HPEXPIRETIME`, `HGETEX`, `HGETDEL`) is the same deadline on a field inside a `hash` entry. Field read after the deadline behaves as absent; the key remains. `SETEX` / `PEXPIRE` / `EXPIREAT` / `TTL` / `PTTL` / `PERSIST` keep operating on the key. The clock is the `013` TTL clock (event-time if the entry has one, else ingest/HLC in the source domain), not a private Redis timer wheel.
- **Rationale**: Spec FR-007. A second expiry implementation would diverge from tombstones and from `gc_grace`. Lazy purge-on-read plus the background job matches both stock Redis (reads do not return expired keys) and `013` (expiry becomes a delete, not a silent omit).
- **Alternatives considered**: Tokio delays per key in the handler (rejected: lost on restart, per-connection, not durable); encoding TTL only in the first-binary side map (rejected: that map is process-local and does not cover hash fields or persistent restore).

## R13. First-binary and `HandlersComplete` dialects do not grow

- **Decision**: No command added by this feature becomes `Must` on `FirstBinary` or `HandlersComplete`. `INFO`, `COMMAND`, `TYPE`, `DBSIZE`, `HGET`, `XADD`, `MULTI`, `SUBSCRIBE`, `PFADD`, and `SETBIT` stay not-supported there, consistent with the current `classify_redis` and with `016` FR-005 / SC-006. `CompleteProduct` (`016` slice 8 / `015` profile) is the first profile that loads the table. `002` `SS.*` canonical commands are unchanged on every profile.
- **Rationale**: Spec FR-015 and the assumption "complete-product scope". `015` `dialect-profiles.md` already says HandlersComplete Redis is "same Redis MUST" as the first binary, and complete product is this table.
- **Alternatives considered**: Enabling collections at slice 6 (rejected: slice 6 is "remaining handlers", not the Redis dialect; the profile table says otherwise); a node config flag that turns the dialect on inside the first binary (rejected: two dialects in one profile is how the first binary stops being testable).

## R14. Conformance is a complete-product feature, stock client, one node

- **Decision**: Tests live in `crates/conformance` behind feature `redis-dialect`, built only with the complete-product profile. They use the existing `redis` Rust client (already the `002` stock-client dev-dependency) against one in-process node, two or more connections when the story needs a publisher, a second consumer, or a `WATCH` racer. Restart cases boot the same data dir twice for persistent streams (FR-016) and assert memory-mode emptiness and no pub/sub replay. First-binary CI gains no new MUST verbs; it keeps the existing "off-list command errors" test. Accuracy for HLL: a fixed fixture of N distinct elements must land inside `1.04/√m` of N at precision 14, asserted as a bound, not as an exact integer.
- **Rationale**: Spec SC-001–SC-008. Unmodified stock client is the constitution V promise. Multi-node pub/sub is out of scope (R9). An exact HLL equality assertion would be a flaky test.
- **Alternatives considered**: Shelling `redis-cli` in CI (unnecessary once the Rust client covers RESP2); running the full table on the first-binary job (rejected: R13); a probabilistic HLL test without a bound (rejected: SC-007 is a bound).

## Integration Testing notes

- The suite is the `002` conformance harness (in-process node, ephemeral port, users file) plus a complete-product dialect profile. It does not start a second binary.
- Contract fixtures under `contracts/fixtures/` are validated like `015`: `complete-product-redis.conf` parses, `max-block-negative.conf` fails validate.
- Cross-protocol check (FR-003 shared object): write a string via Redis `SET`, read the same key as a canonical value through the PostgreSQL or `SS.GET` path on that container, and confirm the entry type is visible. One test, not a new matrix.
- Durable stream test reuses the `013` kill-and-restart pattern; it does not add a WAL format.
- No test requires Lua, geo, or a Redis Cluster gossip socket.

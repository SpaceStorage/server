# Feature Specification: Multiparadigm Type System (L0–L4)

**Feature Branch**: `003-type-system`

**Created**: 2026-09-13

**Status**: Draft

**Input**: User description: "Read .specify/intent/03-type-system.md and specify this feature." — the intent file describes the datatype levels that make SpaceStorage multiparadigm: L0 foundation primitives (data structures such as tuple, vector, linked list, stack/queue/deque, ring buffer, hash table, B+tree, skip list, radix tree, heap, Bloom filter, KD-tree, HNSW, ScaNN, bitmap; storage primitives MemTable, SSTable, WAL, append-only segment; the LSM Tree layout) that work in memory, on persistent storage, or in hybrid mode and accept different encodings (Gorilla, delta, dictionary, RLE), compression (Snappy, ZSTD, LZ4), and encryption (different algorithms and keys); L1 shared capabilities (replication, sharding, partitioning, placement, failure handling, rebalancing, consistency, persistent placement, labels, distributed transactions, consensus, leader election, quorum) defined as a capability layer over types rather than a separate database; L2 data abstractions (maps, sets, sequences, documents, field indexes, key/value, bitmap/n-gram/range/spatial indexes, vector collections, time-series segments, objects); L3 storage models (relational and columnar tables, document store, full-text, vector and spatial search, K/V store, time series, object storage, log stream); and L4 cross-level composition (union, federated, materialized view, and distributed/partitioned/replicated/sharded compositions of placement). Inventories are expandable. Users pick the type that matches the workload instead of running several databases, and drivers and query execution see one abstract type interface.

## Clarifications

### Session 2026-09-13

- Q: Which L0 foundation primitives should be directly creatable as named containers in a namespace? → A: Every L0 data structure (`Tuple`, `Vector`, `Linked List`, `Stack / Queue / Deque`, `Ring Buffer`, `Hash Table`, `B+tree`, `Skip List`, `Radix Tree / Patricia Trie`, `Heap`, `Bloom Filter`, `KD-tree`, `HNSW`, `ScaNN`, `Bitmap / Bitset`) is directly creatable as a container; storage primitives (`MemTable`, `SSTable`, `WAL`, `Append-only Segment`) and storage layouts (`LSM Tree`) are never directly creatable and exist only inside the layout of a higher-level type.
- Q: After a node restart, what happens to a memory-mode container with no replicas? → A: The definition survives, the content does not. The container is restored empty, its description states that its content did not survive the restart, and replication (a shared capability) is the only way content returns. Memory mode is therefore explicitly a volatile tier; durability requires persistent mode, hybrid mode, or replication.
- Q: Can clients write through an L4 composition? → A: Per composition kind. `Materialized View` and `Union` are read-only; `Federated`, `Partitioned`, `Sharded`, `Replicated`, and `Distributed` accept writes and route each write to the single member its key or placement rule selects. A write that no rule resolves to exactly one member is refused, naming the composition and the ambiguity; cross-member atomic writes are not a composition feature and require the distributed transactions capability of L1.
- Q: Who owns per-container schema definition and evolution? → A: This feature, with additive evolution. The type system defines, stores, and validates each container's schema (columns, fields, field paths, dimensions, key definitions, and per-field encoding choices) as part of the container definition. Backward-compatible changes — adding a field or column, widening a value domain, adding an index or field path — apply in place to a live container. Incompatible changes — dropping or renaming a field, narrowing a domain, changing a field's type, changing a key or dimension — are refused and directed to the transform mechanism of the migration and transforms feature.
- Q: What does a container's encryption setting cover? → A: A declared scope, defaulting to drives only. Encryption is declared per container as an algorithm, a key reference, and a scope of either `drives` (default: data encrypted on drives, memory-resident data in plaintext) or `drives and memory` (data also encrypted in memtables, caches, and memory-mode content, with transient per-operation buffers exempt and documented). A memory-mode container may only declare scope `drives and memory`, because scope `drives` would protect nothing there.

### Session 2026-09-15

- Q: Which encryption algorithms must the catalog implement? → A: AES-256-GCM (default) and ChaCha20-Poly1305. Keys are **references**; master key / KEK authority is `14`. Encryption at rest remains opt-in per container; unencrypted persistent data on a stolen disk is an operator-chosen leak.
- Q: What scalar value domains must the catalog include, and how do empty/deleted states differ? → A: At least bool, int32, int64, uint64, float32, float64, decimal, utf8, bytes, uuid, timestamp (UTC, microsecond precision), date, jsonb, and null. **Null** (typed empty), **missing field**, and **tombstone** (deleted, `13`) are three different states. Default collation is Unicode; a container MAY request binary comparison. Vector types MUST declare dimension and distance metric (`l2`, `cosine`, `inner_product`).
- Q: Does memory-mode content survive a process restart? → A: Definitions and options yes; content no, unless replication (`04`) re-populates it. Persistent and hybrid content returns from drives (`13`). Hybrid policy (what stays in memory vs on disk) is per type in the catalog.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Create a storage-model container that matches the workload (Priority: P1)

A schema designer working inside a namespace picks the storage model that fits the data — a relational table for orders, a document store for profiles, a vector search container for embeddings, a time series for sensor readings, an object storage for files, a log stream for events — names it, creates it, and starts writing and reading it through whichever protocol the team already uses. Nothing else has to be installed or configured: every storage model comes with a working default foundation layout. The container permanently carries its type, and describing the container shows the type, its level, the layout behind it, and the options in effect.

**Why this priority**: This is the product promise — one store, many paradigms, chosen per container. Without typed containers at the storage-model level there is nothing for protocols, placement, or the planner to operate on.

**Independent Test**: Can be fully tested on a single node by creating one container of each of the ten L3 storage models in a namespace with no layout options, describing each, writing and reading a small dataset in each, invoking one operation from each model's operation set, and dropping each. Delivers a typed, multiparadigm namespace with no other feature present beyond the runtime and one protocol.

**Acceptance Scenarios**:

1. **Given** a namespace `N` with no containers, **When** a schema designer creates a container `orders` of type `Relational Table` without specifying any layout option, **Then** the container exists in `N` with type `Relational Table` at level L3, the description reports the model's default layout and options marked as defaults, and a row written to it is read back unchanged.
2. **Given** a namespace `N`, **When** the designer creates one container for each of `Relational Table`, `Columnar Table`, `Document Store`, `Full-text Search`, `Vector Search`, `Spatial Search`, `K/V Store`, `Time Series`, `Object Storage`, and `Log Stream`, **Then** all ten are created, each is described with its own type name and level L3, and each accepts a write and returns it on read.
3. **Given** a container of type `T`, **When** a client invokes an operation that belongs to `T`'s operation set (for example a nearest-neighbour search on `Vector Search`, a time-range read on `Time Series`, an append on `Log Stream`, a range read on `K/V Store`), **Then** the operation executes and returns a result shaped as the operation defines.
4. **Given** a container of type `T`, **When** a client invokes an operation that is not in `T`'s operation set (for example a nearest-neighbour search on `Log Stream`), **Then** the request is rejected before touching data, and the error names the container, its type, the operation, and where to find the type's operation set.
5. **Given** a create request naming a type that is not in the inventory, **When** it is submitted, **Then** it is rejected with an error naming the unknown type and listing the container-creatable types of the requested level (or of all levels if no level was given).
6. **Given** a container `orders` already exists in namespace `N`, **When** a second `orders` is created in `N`, **Then** it is rejected; **When** `orders` is created in a different namespace `M`, **Then** it succeeds and the two containers are independent.
7. **Given** an existing container, **When** its description is requested, **Then** the response shows: name, namespace, type name, level, kind, its schema where the type has one, storage mode, the foundation primitives in its layout, encoding per data kind, compression codec, encryption algorithm and key reference (never key material), the shared capabilities declared on it, its composition sources (if any), and which of these values are defaults versus explicitly set.
8. **Given** an existing container of type `T1`, **When** a designer attempts to alter its type to `T2`, **Then** the alteration is rejected with an error stating that a container's type is fixed for its lifetime and pointing to the transform mechanism of the migration and transforms feature.
9. **Given** a container that no composition depends on, **When** it is dropped, **Then** it disappears from the namespace, its name becomes reusable, and its storage is released; **Given** a container that a composition depends on, **When** it is dropped without an explicit cascade, **Then** the drop is refused and the error lists the dependent compositions.
10. **Given** a type the catalog marks schema-required (for example `Relational Table`), **When** a container of it is created with a schema of columns and their value domains, **Then** the schema is validated against the type descriptor, stored with the definition, reported in the description, and enforced on every write; **When** a container of that type is created with no schema, **Then** creation is refused naming the mandatory schema elements.
11. **Given** a live container with a schema, **When** a field or column is added, a value domain widened, or an index added, **Then** the change applies without a data rewrite, existing data stays readable, and subsequent writes may use the new element; **When** a field is dropped or renamed, a domain narrowed, a field's type changed, or a key definition or vector dimension changed, **Then** the change is refused with an error naming it and pointing to the transform mechanism.

### User Story 2 - Discover the type inventory and every type's capabilities (Priority: P1)

A schema designer, a storage engineer, an administrator, a protocol driver at startup, the query planner, and the admin UI all ask the same question: what types exist, at which level, what each one can do, how it may be laid out, which shared capabilities it accepts, and what it may be composed from. The type system answers from one catalog. Every type at every level is present, described by a complete descriptor, and the human-readable documentation is consistent with the catalog.

**Why this priority**: The catalog is what makes the type system one system rather than a collection of engines. The drivers feature verifies mapping coverage against it at startup, the planner matches operations against it, and the intent's "do not treat inventories as closed" rule only works if the inventory is discoverable rather than hard-coded in each consumer. Ties with Story 1.

**Independent Test**: Can be fully tested on a single node by requesting the catalog through the admin surfaces, checking that every name from the L0–L4 inventory appears at its level with a complete descriptor, requesting the encoding, compression, encryption, and shared-capability lists, and comparing the catalog of two nodes of the same release. Delivers a discoverable type system without any data written.

**Acceptance Scenarios**:

1. **Given** a running node, **When** the catalog is requested, **Then** it lists every type grouped by level L0, L1, L2, L3, L4, and every name in the inventory of this specification (FR-003 through FR-007) appears exactly once at the stated level.
2. **Given** a type name, **When** its descriptor is requested, **Then** the descriptor contains: name; level; kind (data structure, storage primitive, or storage layout for L0; shared capability for L1; abstraction for L2; storage model for L3; composition for L4); supported storage modes (memory, persistent, hybrid) with the default; operation set; the shared capabilities it is compatible with; the lower-level types it may be composed from and the default layout; applicable encodings, compression codecs, and encryption support; whether it is directly creatable as a container; the current version of its canonical representation; deprecation status; and a starter example.
3. **Given** a running node, **When** the encoding list is requested, **Then** it includes at least `Gorilla`, `Delta encoding`, `Dictionary encoding`, and `RLE`, each with the data kinds it applies to; **When** the compression list is requested, **Then** it includes at least `Snappy`, `ZSTD`, and `LZ4`; **When** the encryption list is requested, **Then** it includes at least `AES-256-GCM` (marked default) and `ChaCha20-Poly1305`, each with key-reference requirements, and states that the algorithm and the key **reference** are selectable per container.
4. **Given** a running node, **When** the shared-capability list is requested, **Then** it includes `replication`, `sharding`, `partitioning`, `node placement`, `failure handling`, `rebalancing`, `consistency`, `persistent placement`, `labels / placement constraints`, `distributed transactions`, `consensus`, `leader election`, and `quorum`, each stating which parameters (if any) a container declares for it and which types are compatible with it.
5. **Given** two nodes running the same release, **When** their catalogs are compared, **Then** they are identical; **Given** a cluster whose nodes run different releases, **When** the cluster catalog is requested, **Then** the differences are reported per node.
6. **Given** a protocol driver starting on a node, **When** it enumerates the container-creatable types from the catalog, **Then** the enumeration is sufficient for the driver to verify that it has a type mapping for each (the startup verification required by the protocol drivers feature), with no other source needed.
7. **Given** a type with a starter example in its descriptor, **When** the example is applied verbatim on a fresh node, **Then** a container of that type is created and the smoke workflow (write, read, one type-specific operation, drop) completes.
8. **Given** the human-readable type documentation, **When** it is compared with the catalog, **Then** every type, encoding, compression codec, encryption algorithm, and shared capability in the catalog is documented and nothing documented is absent from the catalog.

### User Story 3 - Configure a container's foundation layout, encoding, compression, and encryption (Priority: P2)

A storage engineer needs a container to behave differently from the default: keep it entirely in memory, back it with a persistent LSM layout, encode timestamps with delta encoding and values with Gorilla, compress with ZSTD, and encrypt with a chosen algorithm and a chosen key. The engineer sets these options when defining the container (or later, where the change can apply forward), the type system validates each choice against what the type and its primitives support, and the description reflects the result. Two containers in the same namespace may use different keys and different algorithms.

**Why this priority**: Media, encoding, compression, and encryption per container are the difference between a demo store and one that fits real workloads and security requirements. The defaults of Story 1 make this optional, so it follows the P1 stories.

**Independent Test**: Can be fully tested on a single node by creating containers of the same type in memory, persistent, and hybrid modes, with each encoding applied to an applicable data kind, each compression codec, and two different encryption algorithm/key pairs; writing and reading data in each; restarting the node; and submitting invalid combinations. Delivers controllable storage characteristics per container.

**Acceptance Scenarios**:

1. **Given** a `Time Series` container definition that selects persistent mode, the `LSM Tree` layout (`MemTable`, `WAL`, `SSTable`), `Delta encoding` for timestamps, `Gorilla` for numeric values, and `ZSTD` compression, **When** it is created, **Then** the definition is accepted, the description shows every selected option as explicitly set, and data written is read back unchanged.
2. **Given** a `K/V Store` container definition that selects memory mode with a `Hash Table` layout and no compression, **When** it is created and used, **Then** reads and writes succeed, the description states memory mode, and the catalog entry explains that memory mode is a volatile tier whose content is not retained across a process restart on that node unless a shared capability replicates it.
3. **Given** a type whose descriptor supports hybrid mode, **When** a container is defined in hybrid mode, **Then** the description shows the type's hybrid policy (which part of the data is kept in memory and which on persistent storage), and both parts are readable through the same operations.
4. **Given** a definition that selects a storage mode the chosen primitive does not support, **When** it is submitted, **Then** it is rejected before any storage is allocated and the error names the primitive, the requested mode, and the supported modes.
5. **Given** a definition that applies an encoding to a data kind it does not apply to (for example `Gorilla` to text), **When** it is submitted, **Then** it is rejected and the error names the encoding, the data kind, and the encodings applicable to that data kind.
6. **Given** a definition that selects encryption with algorithm `A` and key reference `K1` for container `C1`, and algorithm `B` with key reference `K2` for container `C2`, **When** both are created and written, **Then** the data each container writes to drives is encrypted under its own algorithm and key, the descriptions show algorithm, key reference, and scope only, and no key material appears in any description, log, or configuration output.
6a. **Given** an encrypted container that declares no scope, **When** it is created, **Then** the scope is `drives`, the description marks it as a default, and memory-resident data of that container may be plaintext.
6b. **Given** an encrypted container that declares scope `drives and memory`, **When** it is written, **Then** its memtables, caches, and memory-resident content are encrypted as well as its drive content, and only transient per-operation buffers are exempt.
6c. **Given** a memory-mode container that declares encryption with scope `drives`, **When** the definition is submitted, **Then** it is refused with an error stating that a memory-mode container must use scope `drives and memory`; **When** the same container declares scope `drives and memory`, **Then** it is created and its whole content is encrypted in memory.
7. **Given** a definition whose key reference cannot be resolved, **When** it is submitted, **Then** creation is rejected naming the key reference, and no data is ever written unencrypted for that container.
8. **Given** an existing container with compression `Snappy`, **When** the engineer changes the compression to `LZ4`, **Then** newly written data uses `LZ4`, previously written data remains readable, the description lists both codecs as present until the old data is rewritten, and the engineer is told that a transform is required to rewrite existing data.
9. **Given** an existing encrypted container, **When** the engineer changes the key reference, **Then** newly written data uses the new key, previously written data remains readable under the old key, the description lists both key references as present, and re-encryption of existing data is available through the transform mechanism.
10. **Given** a container definition with no layout, encoding, compression, or encryption option, **When** it is created, **Then** the type's documented defaults apply and the description marks every one of them as a default.
11. **Given** a node restart, **When** the node comes back, **Then** every persistent and hybrid container on that node is restored with its definition, its data, and its options intact; every memory-mode container is restored with its definition and options but empty, and its description states that its content did not survive the restart.
12. **Given** a memory-mode container with a replica on another live node, **When** the node restarts, **Then** the container is restored empty and is re-populated from the replica by the declared shared capability, and the description shows the re-population state rather than claiming the content survived locally.

### User Story 4 - Apply shared (L1) capabilities to a compatible container (Priority: P2)

A schema designer wants a container replicated three times with replicas in different availability zones, sharded by customer, and written with a chosen consistency behaviour. These are shared capabilities of the L1 layer. The designer declares them on the container; the type system checks that the container's type is compatible with each capability and passes the declaration to the placement machinery. The same declarations work on an L2 abstraction, an L3 model, or an L4 composition; there is no separate "distributed" product to configure.

**Why this priority**: The intent requires L1 to be a capability layer over types. Getting the compatibility contract right is what prevents a parallel distributed type hierarchy from appearing later. The placement semantics themselves belong to the distribution feature, so this story is about declaration and validation and can follow the local stories.

**Independent Test**: Can be fully tested on a single node with a placement stub that records declarations: declare each shared capability on compatible and incompatible types and verify acceptance, rejection, and what is passed on. Delivers a validated capability contract independent of a multi-node cluster.

**Acceptance Scenarios**:

1. **Given** a `Document Store` container definition declaring replication factor 3 with anti-affinity by the `az` label and sharding by a document field, **When** it is created, **Then** the definition is accepted, the description shows the declared capabilities, and the declaration is handed to the placement layer unchanged.
2. **Given** a type whose descriptor marks a shared capability as incompatible, **When** a definition declares that capability on a container of that type, **Then** it is rejected before any placement occurs and the error names the type, the capability, and the capabilities the type is compatible with.
3. **Given** an L2 abstraction such as `Ordered Map`, **When** replication is declared on it, **Then** it is accepted under the same rules and reported in the same form as for an L3 model; the level of the type does not change how a compatible capability is declared.
4. **Given** a container created without any shared-capability declaration, **When** it is described, **Then** the description states that no capability was declared and that the placement layer's defaults apply, and names those defaults as reported by the placement layer.
5. **Given** an L3 model composed from several lower-level primitives, **When** shared capabilities are declared on the container, **Then** they apply to the container as one unit: every component primitive is placed and replicated with the container, and a definition that tries to give one component a different placement from its container is rejected.
6. **Given** a container with declared capabilities, **When** the designer later changes a capability parameter (for example replication factor from 2 to 3), **Then** the change is validated against the type's compatibility, accepted when compatible, and handed to the placement layer as a change to an existing placement; **When** the change is to a parameter the type declares as fixed after creation (for example the sharding key), **Then** it is rejected with a pointer to the migration and transforms feature.
7. **Given** a new shared capability added to the L1 inventory in a later release, **When** the catalog is inspected, **Then** every existing type reports the new capability as incompatible until the type's descriptor explicitly declares compatibility.

### User Story 5 - Compose storage objects across levels (L4) (Priority: P2)

A schema designer combines existing containers into one logical storage object: a union of this quarter's and last quarter's tables, a federated object over a document store and a relational table, a materialized view kept up to date from a source container, or a partitioned, sharded, replicated, or distributed composition that places members by key range or label. The composition is itself a container: it has a name and a type, lives in a namespace, is described like any container, is visible through every protocol, and declares which operations it supports given its members.

**Why this priority**: Composition is how users avoid running several databases side by side. It depends on Stories 1 and 4 having containers and placement declarations to compose.

**Independent Test**: Can be fully tested on a single node by creating members of several types, composing each L4 kind over them, describing and reading through the composition, dropping a member with and without cascade, and attempting a cyclic and a cross-namespace composition. Delivers cross-level composition without a cluster.

**Acceptance Scenarios**:

1. **Given** two `Relational Table` containers with compatible schemas, **When** a `Union` composition is created over them, **Then** a read through the union returns the rows of both, the description lists both members and marks the union read-only, and a write addressed to the union is refused with an error naming the kind and pointing at the members.
2. **Given** a `Document Store` and a `Relational Table`, **When** a `Federated` composition is created over them, **Then** the composition is readable as one logical object, each member keeps its own type and remains directly usable, the composition's operation set (as computed from its members and shown in the description) is what the planner and drivers see, a write whose key resolves to exactly one member is routed there and stored, and a write that resolves to none or to several is refused naming the ambiguity with nothing stored.
3. **Given** a source container and a definition of a `Materialized View` over it with a declared freshness policy (synchronous or asynchronous), **When** the view is created and the source is written, **Then** the view reflects the write according to the policy, the description shows the sources, the policy, and the last refresh state, and a read of the view does not require the reader to know the sources.
4. **Given** a composition `X` whose member set would include `X` itself directly or through another composition, **When** it is defined, **Then** it is rejected as cyclic and the error shows the cycle.
5. **Given** a `Materialized View` over a `Union`, **When** it is defined, **Then** nesting is accepted up to the documented depth, each level is validated, and the description shows the full member tree; **When** the documented depth is exceeded, **Then** the definition is rejected naming the limit.
6. **Given** a `Partitioned` composition that places members by key range, or a `Sharded`, `Replicated`, or `Distributed` composition placing members by label, **When** it is created, **Then** the description names the L1 capability each placement rule relies on, the placement itself is executed by the placement layer, the catalog states that these compositions are compositions of placement and introduce no capability that L1 does not have, and a write is routed to the single member the partition, shard, or placement rule selects.
6a. **Given** a `Materialized View`, **When** a client writes to it directly, **Then** the write is refused with an error naming the kind and its sources; the view changes only through refresh from its sources.
6b. **Given** a client that needs one atomic write across several members of a composition, **When** it attempts it through the composition, **Then** the composition does not provide atomicity and the answer directs the client to the distributed transactions capability of L1.
7. **Given** any L4 composition, **When** the namespace is listed through any protocol, **Then** the composition appears with its type name like any other container.
8. **Given** members in two different namespaces, **When** a composition over them is defined, **Then** it is rejected because compositions are scoped to one namespace.
9. **Given** a composition, **When** one of its members is dropped with cascade, **Then** the composition is either dropped or, if the composition kind tolerates a missing member (documented per kind), continues with the remaining members and the description records the removal; **When** the member is dropped without cascade, **Then** the drop is refused (Story 1, scenario 9).
10. **Given** an L4 composition, **When** shared capabilities are declared on it, **Then** they are validated against the composition kind's compatibility exactly as for any other type.

### User Story 6 - Drivers and the planner see every type through one abstract interface (Priority: P3)

A protocol driver receiving a query and the query planner deciding how to execute it never special-case a type. Each type publishes its operation set as capability descriptors — what it can filter, order, aggregate, range-scan, search by similarity, append, or look up — and every operation is invoked through the same abstract type interface. Each type also defines one canonical, versioned, self-describing representation for its values so that a value can travel through any protocol without loss. When a type cannot do what a query asks, the answer is a clear, named refusal rather than a silent scan or a wrong result.

**Why this priority**: This is the seam between the type system and the protocol and execution features. Both of those features already require it; this story pins down what the type system must provide. It can be verified once Stories 1 and 2 exist.

**Independent Test**: Can be fully tested by invoking every operation of every type through the abstract interface from a test harness, querying capabilities without data present, round-tripping values of every type through their canonical representation, and asking for unsupported operations. Delivers the contract consumed by the drivers and query-execution features.

**Acceptance Scenarios**:

1. **Given** the catalog, **When** the capability descriptors of a type are requested, **Then** each operation states its name, inputs, outputs, ordering and filtering guarantees, and whether the type can execute it natively; the response is served from metadata without reading container data.
2. **Given** a query requiring a nearest-neighbour search, **When** the planner consults the capability descriptors of a `Vector Search` container, **Then** it finds a native nearest-neighbour operation; **When** it consults a `Log Stream` container, **Then** it finds none and the type system returns a "not supported by type" answer naming the type and the operation, which the planner can pass to the client.
3. **Given** every type in the inventory, **When** a representative value is converted to the type's canonical representation and back, **Then** the value is identical, the canonical form carries its type name and representation version, and the type system accepts every documented earlier version of the representation on input while emitting the current version on output.
4. **Given** a conformance harness, **When** it invokes every operation listed in the catalog for every type through the abstract interface only, **Then** every operation is reachable that way, and there is no operation a driver or the planner would need that is not in the catalog.
5. **Given** a type added in a later release, **When** the drivers and the planner run unchanged, **Then** they discover the new type and its operations from the catalog and the abstract interface without any change to the interface itself.
6. **Given** a container of any type, **When** it is accessed, **Then** the type system counts the access, the hit or miss where the type has such a notion, and the duration, labelled with the type name, so that the observability feature can publish them per type and the tenancy feature can enforce per-type quotas.

### User Story 7 - Extend the inventory without disturbing existing types (Priority: P3)

A platform maintainer adds a new foundation primitive, a new abstraction, a new storage model, a new composition kind, a new encoding, a new compression codec, or a new encryption algorithm. The addition registers a complete descriptor at exactly one level, appears in the catalog, becomes selectable for new containers, and changes nothing about existing containers or types. A type that is being phased out is marked deprecated and stops accepting new containers, but data in existing containers stays readable.

**Why this priority**: The intent states the lists are not closed and the constitution forbids a parallel type hierarchy. Making extension a defined act with rules keeps future growth inside the five-level architecture. It is a maintainer-facing story and follows the user-facing ones.

**Independent Test**: Can be fully tested on a single node by registering a test type, a test encoding, and a test compression codec with complete descriptors, attempting registrations with missing fields or two levels, creating containers with the new items, deprecating the test type, and confirming existing containers are untouched. Delivers a governed extension path.

**Acceptance Scenarios**:

1. **Given** a complete descriptor for a new type at level L2, **When** it is registered, **Then** the catalog lists it under L2, containers of the new type can be created, every existing container and type descriptor is unchanged, and a protocol driver that lacks a mapping for it reports that at startup as the protocol drivers feature requires.
2. **Given** a descriptor that omits a mandatory field (level, kind, storage modes, operation set, shared-capability compatibility, composition inputs, canonical representation version, or starter example), **When** registration is attempted, **Then** it is rejected naming the missing fields.
3. **Given** a descriptor that names no level or more than one level, **When** registration is attempted, **Then** it is rejected with an error stating that every type belongs to exactly one of L0, L1, L2, L3, L4.
4. **Given** a new encoding registered with its applicable data kinds, or a new compression codec, or a new encryption algorithm with its key requirements, **When** a new container selects it, **Then** it is applied; existing containers keep their codecs and are unaffected.
5. **Given** a type in the catalog with existing containers, **When** it is marked deprecated, **Then** new containers of that type are refused with a message naming the replacement (if any), existing containers remain fully readable and writable, and the catalog shows the deprecation; **When** removal is attempted while any container of the type exists anywhere in the cluster, **Then** removal is refused and the containers are listed.
6. **Given** a new shared capability registered at L1, **When** the catalog is inspected, **Then** it appears with its parameters, and no existing type is compatible with it until its descriptor is updated (Story 4, scenario 7).

### Edge Cases

- L0 storage primitive or layout requested directly as a container (`MemTable`, `SSTable`, `WAL`, `Append-only Segment`, `LSM Tree`): refused with a message naming the L2 and L3 types whose layouts use it. Every L0 data structure, by contrast, is directly creatable (FR-014).
- L0 data structure created directly whose semantics overlap an L2 abstraction (for example a stand-alone `Hash Table` next to a `Key/Value collection`): both are legitimate containers with different guarantees; the catalog descriptor of each states what the L0 primitive does not provide that the L2 abstraction does, so a designer can choose deliberately.
- Memory-mode container on a node whose in-memory storage is absent or too small for the container: the definition is accepted by the type system (it is type-valid) and the placement layer decides whether any node can host it; the container's description shows "unplaceable" with the reason until a node qualifies.
- Hybrid-mode container whose in-memory portion is exhausted: the type's hybrid policy governs eviction to the persistent part; the operation set does not change, and the description and metrics show the memory portion as full.
- Same encoding requested for two data kinds where it applies to only one: the definition is rejected as a whole; no partial application.
- Compression and encryption both selected: the type system always applies compression before encryption and documents this once for all types; a definition cannot reverse the order.
- Encryption key reference resolvable at creation but not at a later restart: the container is restored as present but unavailable, its description names the unresolvable key reference, no operation returns plaintext, and no data is discarded.
- Encryption scope widened from `drives` to `drives and memory` on a live container: it takes effect for memory-resident data as that data is next populated (memtable flush cycle, cache refill, replica repopulation), and the description shows the requested scope and whether it is fully in effect yet; narrowing the scope back applies immediately and is recorded.
- Dictionary encoding on a data kind whose cardinality later exceeds the type's dictionary policy: the type keeps the data correct (falls back per its documented policy for new segments) and reports the change in the description; it never refuses writes for this reason.
- Two shared-capability declarations that conflict for a type (for example a partitioning key that is not part of the sharding key when the type requires containment): rejected at definition with both declarations named.
- L1 capability declared on an L4 composition whose members already declare their own: the composition's declaration governs the composition object itself (for example its metadata and view state); member placement stays with the members; the description shows both so operators see no hidden override.
- `Union` over members of different types: refused unless the catalog lists the type pair as union-compatible; `Federated` is the composition kind for heterogeneous members.
- `Materialized View` whose source becomes unavailable (all replicas down): the view keeps serving its last refreshed state, reports staleness in its description and metrics, and a refresh attempt reports the source's unavailability rather than clearing the view.
- Composition member renamed: compositions reference members by identity, not by name, so the composition continues to work and the description shows the new name.
- Container name valid in one namespace but colliding with a protocol's naming rules: the type system stores the name as given; reversible escaping is the drivers feature's concern.
- Type deprecated while a composition of that type exists: the composition continues to work; new compositions of that kind are refused like any deprecated type.
- Two nodes of different releases where one knows a type the other does not: a container of that type is placed only on nodes that know it; the cluster catalog shows the per-node difference; nothing is silently downgraded.
- Descriptor for a type marks an operation as supported that the implementation cannot perform: the conformance harness (Story 6, scenario 4) fails; a catalog entry that overstates capabilities is a defect, not a permitted discrepancy.
- Schema-free or schema-optional type (for example `K/V Store`, `Object Storage`, `Log Stream`, or a `Document Store` used without a declared mapping): the container is created with no schema, writes are validated only against the type's own constraints, and a later schema addition applies to subsequent writes without invalidating existing data.
- Additive schema change submitted concurrently with writes to the same container: the change either applies before or after a given write, never partially; a write validated against the older schema remains valid, since additive changes never invalidate stored data.
- Two protocol drivers describing the same container: both read the schema from the type system and render it in their own protocol's form, so a column added through one protocol is visible through the other without a second schema store.
- Value that fits a type's canonical representation but not the type's declared constraints (for example a vector of the wrong dimension for a `Vector collection` configured for a fixed dimension): rejected naming the constraint; nothing is stored.

## Requirements *(mandatory)*

### Functional Requirements

**Levels and inventory**

- **FR-001**: The type system MUST organise every type into exactly one of five levels: L0 foundation primitives, L1 shared capabilities, L2 data abstractions, L3 storage models, L4 storage composition. A type MUST NOT exist outside these levels or in more than one, and no parallel hierarchy MAY be introduced.
- **FR-002**: Every inventory in this specification MUST be treated as expandable. The type system MUST provide a defined registration path for new types, encodings, compression codecs, encryption algorithms, and shared capabilities (FR-045 through FR-049) and MUST NOT require changes to existing types when an item is added.
- **FR-003**: The L0 inventory MUST include at least the following foundation primitives, classified by kind: data structures `Tuple`, `Vector`, `Linked List`, `Stack / Queue / Deque`, `Ring Buffer`, `Hash Table`, `B+tree`, `Skip List`, `Radix Tree / Patricia Trie`, `Heap`, `Bloom Filter`, `KD-tree`, `HNSW`, `ScaNN`, `Bitmap / Bitset`; storage primitives `MemTable`, `SSTable`, `WAL`, `Append-only Segment`; storage layouts / engines `LSM Tree`.
- **FR-004**: The L1 inventory MUST include at least the shared capabilities `replication`, `sharding`, `partitioning`, `node placement`, `failure handling`, `rebalancing`, `consistency`, `persistent placement`, `labels / placement constraints`, `distributed transactions`, `consensus`, `leader election`, and `quorum`.
- **FR-005**: The L2 inventory MUST include at least the data abstractions `Map`, `Ordered Map`, `Multimap`, `Set`, `Ordered Set`, `Sequence`, `Document abstraction`, `Field Index`, `Field Path`, `Key/Value collection`, `Bitmap index`, `N-gram index`, `Range index`, `Spatial Index Primitive`, `Vector collection`, `Time-series segment`, `Object`, and `Object Collection`.
- **FR-006**: The L3 inventory MUST include at least the storage models, classified by kind: structured storage `Relational Table`, `Columnar Table`, `Document Store`; indexes `Full-text Search`, `Vector Search`, `Spatial Search`; specialized stores `K/V Store`, `Time Series`, `Object Storage`, `Log Stream`.
- **FR-007**: The L4 inventory MUST include at least the composition kinds `Union`, `Federated`, and `Materialized View`, and the distribution composition kinds `Distributed`, `Partitioned`, `Replicated`, and `Sharded`.
- **FR-008**: The distribution composition kinds of L4 MUST be defined as compositions of L1 placement capabilities. Each MUST name the L1 capabilities it relies on in its descriptor and MUST NOT introduce any placement capability that is not in L1.
- **FR-008a**: Write behaviour MUST be fixed per composition kind, not per composition definition. `Materialized View` and `Union` MUST be read-only: a write addressed to them is refused with an error naming the kind and directing the client to the members (for `Union`) or the sources (for `Materialized View`). `Federated`, `Partitioned`, `Sharded`, `Replicated`, and `Distributed` MUST accept writes and MUST route each write to the single member selected by the composition's key or placement rule; a write that the rule does not resolve to exactly one member MUST be refused naming the composition and the ambiguity, with nothing stored. A composition MUST NOT implement atomicity across several members; a client needing that MUST use the distributed transactions capability of L1.

**Type descriptors and catalog**

- **FR-009**: Every type MUST have a descriptor containing at least: a stable name; level; kind; supported storage modes (memory, persistent, hybrid) with the default; operation set expressed as capability descriptors (FR-039); the shared capabilities it is compatible with, including which parameters are declared at definition time and which are fixed after creation; the lower-level types it MAY be composed from and its default layout; applicable encodings, compression codecs, and encryption support; whether it is directly creatable as a container; the current version of its canonical representation and the accepted earlier versions; deprecation status; and a starter example.
- **FR-010**: The type system MUST publish a catalog of every registered type, encoding, compression codec, encryption algorithm, and shared capability, with full descriptors, through the abstract type interface and through the node's admin surfaces and bundled CLI.
- **FR-011**: The catalog MUST be identical on every node running the same release, and the cluster MUST be able to report per-node catalog differences when nodes run different releases.
- **FR-012**: The catalog MUST be sufficient for a protocol driver to enumerate every container-creatable type and for the query planner to learn every operation of every type, with no other source of type knowledge required.
- **FR-013**: Human-readable documentation MUST exist for every catalog item and MUST be consistent with the catalog; each type's starter example MUST work verbatim on a fresh node.
- **FR-014**: Every L0 data structure (`Tuple`, `Vector`, `Linked List`, `Stack / Queue / Deque`, `Ring Buffer`, `Hash Table`, `B+tree`, `Skip List`, `Radix Tree / Patricia Trie`, `Heap`, `Bloom Filter`, `KD-tree`, `HNSW`, `ScaNN`, `Bitmap / Bitset`), every L2 abstraction, every L3 storage model, and every L4 composition kind MUST be directly creatable as a container. L0 storage primitives (`MemTable`, `SSTable`, `WAL`, `Append-only Segment`) and L0 storage layouts (`LSM Tree`) MUST NOT be directly creatable; they exist only inside the layout of a higher-level type, and a create request naming one MUST be refused with an error naming the types that use it. The catalog MUST mark each type's direct-creatability accordingly.

**Containers**

- **FR-015**: A container MUST be an instance of exactly one container-creatable type, MUST belong to exactly one namespace, MUST have a name unique within that namespace, and MUST carry its type for its whole lifetime; a container's type MUST NOT be changed in place, and the only path to another type is a transform of the migration and transforms feature.
- **FR-016**: The type system MUST support create, describe, alter, and drop for containers of every container-creatable type, and MUST validate every definition against the type's descriptor before any storage or placement is allocated.
- **FR-017**: A container description MUST report name, namespace, type, level, kind, schema (where the type has one), storage mode, layout primitives, encoding per data kind, compression codecs present, encryption algorithms and key references present, declared shared capabilities (or that placement defaults apply), composition members and dependants, and for every option whether it is a default or explicitly set. Key material MUST never appear in a description, log, or configuration output.
- **FR-017a**: The type system MUST own each container's schema: the columns, fields, field paths, key definitions, vector dimensions, value domains, and per-field encoding choices that the container's type requires or allows. Every type descriptor MUST state whether its containers are schema-required, schema-optional, or schema-free, and which schema elements are mandatory at creation. The schema MUST be stored with the container definition, MUST be validated against the type descriptor before creation, MUST be reported in the container description, and MUST be the single source of schema truth for protocol drivers; a driver MUST NOT keep a schema of its own.
- **FR-017b**: Backward-compatible schema changes — adding a field, column, or field path, widening a value domain, and adding an index over existing data — MUST be applicable to a live container without a data rewrite, MUST leave existing data readable, and MUST take effect for subsequent writes. Incompatible changes — dropping or renaming a field or column, narrowing a value domain, changing a field's type, and changing a key definition or a vector dimension — MUST be refused with an error naming the change and directing the requester to the transform mechanism of the migration and transforms feature.
- **FR-018**: A definition that names an unknown type, an operation outside the type's operation set, an unsupported storage mode, an inapplicable encoding, an incompatible shared capability, a cyclic or cross-namespace composition, or a missing descriptor field MUST be rejected as a whole with an error naming the offending element and the accepted alternatives; partial application is prohibited.
- **FR-019**: Dropping a container that other containers depend on (as composition member or materialized-view source) MUST be refused unless cascade is requested; with cascade the dependants MUST be dropped or, where the composition kind documents tolerance for a missing member, updated and recorded as such.
- **FR-020**: Every container MUST be usable through every protocol handler via the abstract type interface, and the type system MUST expose the container's type name to any listing operation, for every L0 data structure, L2 abstraction, L3 storage model, and L4 composition.

**L0 storage modes, encodings, compression, encryption**

- **FR-021**: Every L0 primitive MUST declare which of the storage modes memory, persistent, and hybrid it supports and MUST operate correctly in each declared mode; the type system MUST reject a definition requesting an undeclared mode.
- **FR-022**: Memory mode MUST keep the container's content entirely in the node's declared in-memory storage; persistent mode MUST keep the content durably on the node's drives (memory MAY be used as a cache); hybrid mode MUST keep a declared portion in memory and the rest on drives under a policy stated in the type's descriptor. The three modes MUST present the same operation set for the same type.
- **FR-023**: Every persistent and hybrid container MUST be restorable with its definition, data, and options after a node restart. A memory-mode container MUST be restored with its definition and options but MUST NOT be expected to retain its content: it comes back empty unless a shared capability re-populates it from a replica, and its description MUST state that the content did not survive the restart. The catalog and the starter documentation MUST state that memory mode is a volatile tier and that durability requires persistent mode, hybrid mode, or replication.
- **FR-024**: Every L0 primitive MUST be able to use encodings, compression, and encryption independently of one another, and the type system MUST support at least the encodings `Gorilla`, `Delta encoding`, `Dictionary encoding`, and `RLE`; the compression codecs `Snappy`, `ZSTD`, and `LZ4`; and encryption algorithms `AES-256-GCM` (default) and `ChaCha20-Poly1305`, with per-container key **reference** and scope selection. Key material and KEK unwrap are `14`.
- **FR-024a**: The catalog MUST include at least the value domains: bool, int32, int64, uint64, float32, float64, decimal, utf8, bytes, uuid, timestamp (UTC, microsecond precision), date, jsonb, and null. **Null**, **missing field**, and **tombstone** MUST be three different states (tombstone lifetime is `13`). Default collation MUST be Unicode; a container MAY request binary comparison. Vector types MUST declare dimension and distance metric (`l2`, `cosine`, `inner_product`).
- **FR-024b**: The catalog MAY include a `multi_active` flag per type (default off; ordered/log types forced off). Create with `multi_active=on` is refused in the first binary (`12`/`16`); this feature only stores the flag.
- **FR-025**: Every encoding MUST declare the data kinds it applies to; the type system MUST allow encodings to be chosen per data kind (for example per column or field) within one container and MUST reject an encoding applied to a data kind it does not cover.
- **FR-026**: Compression MUST be selectable per container from the registered codecs; the type system MUST apply compression before encryption when both are selected and MUST document this once for all types.
- **FR-027**: Encryption MUST be selectable per container as an algorithm, a key reference, and a scope; two containers in one namespace MUST be able to use different algorithms, different keys, and different scopes; the key reference MUST resolve through the key authority of the authz-and-keys feature (`14`); an unresolvable key reference MUST prevent creation and, at restart, MUST leave the container present but unavailable with no plaintext access and no data loss. Encryption at rest is opt-in; unencrypted persistent data is an operator-chosen leak (`14`).
- **FR-027a**: The encryption scope MUST be one of `drives` or `drives and memory` and MUST default to `drives`. Scope `drives` MUST encrypt everything the container writes to drives and MAY hold memory-resident data in plaintext. Scope `drives and memory` MUST additionally encrypt the container's memory-resident stored data, including memtables, caches, and the whole content of a memory-mode container; transient buffers used within a single operation are exempt and this exemption MUST be documented. A memory-mode container that declares encryption MUST declare scope `drives and memory`; scope `drives` on a memory-mode container MUST be refused, because it would protect nothing. The scope in effect MUST appear in the container description.
- **FR-028**: Changing a container's compression codec, encoding, or encryption key after creation MUST apply to newly written data while previously written data remains readable under its original settings; the description MUST list every codec, encoding, and key reference present; rewriting existing data MUST be offered through the transform mechanism, not performed implicitly.
- **FR-029**: Every type MUST have documented defaults for storage mode, layout, encoding, compression, and encryption such that a container can be created with no L0 options at all.

**L1 as a capability layer**

- **FR-030**: L1 MUST be a capability layer applied to compatible types at any level (L0 directly creatable primitives, L2, L3, L4) and MUST NOT be a separate database, product, or type hierarchy. Declaring a shared capability MUST use the same form regardless of the level of the container's type.
- **FR-031**: Every type descriptor MUST state, for each shared capability in the L1 inventory, whether the type is compatible with it, which parameters are declared at definition time (for example replication factor, anti-affinity label, sharding key, partition scheme, consistency mode, persistent placement), and which of those are fixed after creation. A newly registered capability MUST default to incompatible for every existing type.
- **FR-032**: The type system MUST validate every shared-capability declaration against the type's compatibility before handing it to the placement layer and MUST reject incompatible or mutually conflicting declarations naming the type, the capability, and the compatible alternatives.
- **FR-033**: Shared capabilities declared on a container MUST apply to the container as one unit: all component primitives of the container's layout MUST be placed, replicated, and recovered together, and a definition that gives a component its own placement MUST be rejected.
- **FR-034**: A container with no shared-capability declaration MUST be described as using the placement layer's defaults, and the description MUST name those defaults as reported by the placement layer.
- **FR-035**: Changing a shared-capability parameter after creation MUST be validated like a new declaration; parameters the descriptor marks as fixed MUST be refused with a pointer to the migration and transforms feature.
- **FR-036**: The semantics of each shared capability (how replicas are placed, what a consistency mode or quorum means, how failures are handled and rebalanced, how distributed transactions, consensus, and leader election operate) are owned by the distribution and placement feature and the control-plane feature; the type system MUST carry the declarations and compatibility and MUST NOT redefine those semantics.

**L2 and L3 composition rules**

- **FR-037**: Every L2 abstraction and L3 storage model MUST declare in its descriptor the L0 primitives and, for L3, the L2 abstractions it MAY be composed from, together with a default layout; an L3 model MAY use L0 primitives or L1-enabled primitives directly when its descriptor allows it.
- **FR-038**: A container's layout MUST be chosen only from the compositions its type's descriptor allows; the type system MUST reject a layout that uses a primitive the descriptor does not list for that type.

**Operation sets, abstract interface, canonical representation**

- **FR-039**: Every type MUST publish its operation set as capability descriptors stating, per operation: name, inputs, outputs, ordering and filtering guarantees, and whether the type executes it natively. Capability queries MUST be answerable from metadata without reading container data.
- **FR-040**: The type system MUST provide one abstract type interface through which every operation of every type is invoked, every container is created, described, altered, listed, and dropped, and the catalog is read. Protocol drivers and the query execution layer MUST use only this interface; there MUST be no type-private access path required by any consumer.
- **FR-041**: An operation invoked on a type whose operation set does not include it MUST be refused before touching data with an answer naming the type and the operation; the type system MUST NOT substitute a different operation or return partial results.
- **FR-042**: Every type MUST define exactly one canonical, self-describing, versioned representation of its values. Round-tripping any value through the canonical representation MUST be lossless; the type system MUST accept every documented earlier version on input and MUST emit the current version on output. This representation is the fallback carried by protocol drivers when a protocol has no native form for the type.
- **FR-043**: A value that violates a container's declared constraints (dimension, schema, key uniqueness, ordering rule, or similar, as the type defines) MUST be rejected naming the constraint, and nothing MUST be stored for that write.
- **FR-044**: Every container MUST count accesses, hits and misses (where the type has that notion), and operation duration, labelled with the type name and namespace, and MUST expose resource usage per type so that the observability feature can publish them and the tenancy feature can enforce per-type quotas.

**Extending the inventory**

- **FR-045**: Registering a new type MUST require a complete descriptor (FR-009) at exactly one level; incomplete or multi-level descriptors MUST be rejected naming the missing or conflicting fields.
- **FR-046**: Registering a new type, encoding, compression codec, encryption algorithm, or shared capability MUST NOT alter any existing type descriptor or existing container, and the new item MUST become selectable for new containers immediately after registration and appear in the catalog.
- **FR-047**: A type MAY be marked deprecated: new containers of that type MUST be refused with a message naming the replacement if one exists, existing containers MUST remain fully usable, and the catalog MUST show the status.
- **FR-048**: A type MUST NOT be removed from the inventory while any container of that type exists anywhere in the cluster; removal attempts MUST be refused listing those containers.
- **FR-049**: A catalog entry that claims a capability, storage mode, encoding, or operation the type cannot actually provide is a conformance failure; the type system MUST ship a conformance harness that exercises every catalog claim through the abstract interface.

### Key Entities

- **Type Level**: One of L0 foundation primitives, L1 shared capabilities, L2 data abstractions, L3 storage models, L4 storage composition. Every type belongs to exactly one.
- **Type**: A named, registered kind of storage behaviour at one level, described by a Type Descriptor. The current inventories are listed in FR-003 through FR-007 and are expandable.
- **Type Descriptor**: The complete metadata record of a type (FR-009): name, level, kind, storage modes, operation set, shared-capability compatibility, composition inputs and default layout, applicable encodings/compression/encryption, direct-creatability flag, canonical representation versions, deprecation status, starter example.
- **Type Catalog**: The node's and cluster's published set of descriptors for types, encodings, compression codecs, encryption algorithms, and shared capabilities; identical per release; readable through the abstract interface, admin surfaces, and CLI.
- **Container**: A named instance of one container-creatable type inside one namespace, with a Layout, L0 options, declared Shared Capabilities, optional Composition membership, and a lifetime-fixed type.
- **Container Schema**: The columns, fields, field paths, key definitions, vector dimensions, value domains, and per-field encoding choices of one container, owned and validated by the type system, stored with the definition, and the single source of schema truth for every protocol driver. A type is schema-required, schema-optional, or schema-free per its descriptor; evolution is additive in place, and incompatible changes go through the transform mechanism.
- **Layout**: The set of L0 primitives (and, for L3, L2 abstractions) backing a container, chosen from the type's allowed compositions; has a documented default per type.
- **Storage Mode**: memory, persistent, or hybrid; declared per primitive and selected per container; hybrid carries a per-type policy for the in-memory portion.
- **Encoding**: A registered value encoding (`Gorilla`, `Delta encoding`, `Dictionary encoding`, `RLE`, and future additions) with the data kinds it applies to; chosen per data kind within a container.
- **Compression Codec**: A registered codec (`Snappy`, `ZSTD`, `LZ4`, and future additions) chosen per container; applied before encryption.
- **Encryption Setting**: An algorithm (`AES-256-GCM` default, or `ChaCha20-Poly1305`), a key reference, and a scope (`drives`, the default, or `drives and memory`) chosen per container; scope `drives and memory` covers memtables, caches, and memory-mode content, exempting only transient per-operation buffers, and is mandatory when a memory-mode container is encrypted. Key material is resolved through `14` and never stored or displayed by the type system.
- **Value Domain**: A scalar type from FR-024a used in schemas. Distinct from null, missing field, and tombstone.
- **Shared Capability (L1)**: One of the thirteen capabilities in FR-004 (or a later addition), with the parameters a container declares for it; compatibility is stated per type; semantics live in the distribution and control-plane features.
- **Capability Compatibility Matrix**: For every (type, shared capability) pair: compatible or not, declarable parameters, and which parameters are fixed after creation; new capabilities default to incompatible.
- **Composition (L4)**: A container of kind `Union`, `Federated`, `Materialized View`, `Distributed`, `Partitioned`, `Replicated`, or `Sharded` whose members are other containers in the same namespace, referenced by identity; acyclic; nesting bounded by a documented depth. Write behaviour is a property of the kind: read-only for `Union` and `Materialized View`, single-member routed for the rest. Each kind also documents its missing-member tolerance and, for the distribution kinds, the L1 capabilities it composes.
- **Operation / Capability Descriptor**: One operation of a type's operation set with name, inputs, outputs, ordering and filtering guarantees, and native-execution flag; queried by the planner and drivers from metadata.
- **Abstract Type Interface**: The single contract through which every consumer creates, describes, alters, lists, drops containers, reads the catalog, and invokes operations on every type.
- **Canonical Representation**: The single self-describing, versioned value representation defined per type; lossless round-trip; earlier versions accepted on input, current version emitted on output; used by protocol drivers as the universal fallback.

## Assumptions

- Type names, level names, encoding, compression, and encryption algorithm names, and shared-capability names in this specification are product requirements (per `.specify/intent/README.md` reading rules), not implementation choices. No language, runtime, or library is named; those mandates live in the constitution.
- **Which types are containers**: every L0 data structure, every L2 abstraction, every L3 storage model, and every L4 composition kind is directly creatable as a container; only L0 storage primitives and the `LSM Tree` layout are not (confirmed in Clarifications, Session 2026-09-13). The protocol drivers feature's requirement to reach "every type in the inventory" therefore covers all of L0 data structures and L2–L4: the cross-protocol mapping and conformance matrix is sized accordingly. The intent's actor split still holds in practice — a schema designer normally works at L2–L4 and a storage engineer configures L0 as layout — but nothing prevents creating an L0 data structure directly.
- **Memory mode and restart**: the constitution's "restore state of all local datatypes in drives or memory" is read as: definitions and options of every container are always restored; content of persistent and hybrid containers is restored from drives; content of a memory-mode container does not survive a process restart on that node, and the container comes back empty unless replication re-populates it (confirmed in Clarifications, Session 2026-09-13). Memory mode is documented as a volatile tier. Durability-through-replication semantics belong to the distribution feature.
- **Hybrid mode** means a per-type policy for which part of the data lives in memory (for example the `MemTable` of an `LSM Tree`, a hot set, or recent time-series segments) with the rest persistent; the policy is a descriptor field and a planning decision per type.
- **Compression before encryption** is fixed for all types so that encryption never hides compressible structure and so that the rule is stated once.
- **Key management** (master key, namespace KEKs, rotation, who may bind a key) belongs to `14`; the type system consumes a key reference and honours per-container algorithm, key, and scope choice. Encryption at rest is opt-in (Clarifications, Session 2026-09-15).
- **Value domains** listed in FR-024a are product requirements, not planning leftovers. Null, missing field, and tombstone are distinct (tombstone retention `13`).
- **Encryption scope** is declared per container and defaults to `drives`, so an encrypted container protects drive content unless the operator asks for memory coverage too (confirmed in Clarifications, Session 2026-09-13). The one forced case is a memory-mode container, where scope `drives` would be a silent no-op and is therefore refused. The exact boundary of "transient per-operation buffer" is a planning decision and must be documented so the guarantee is not overstated.
- **Shared capabilities are declared at container level** and inherited by all layout components; a component of one container never has independent placement. Declarations on an L4 composition govern the composition object; members keep their own declarations. Capability semantics, including quorum vocabulary and sync/async replication, are owned by the distribution feature (`04`) and controller behaviour by the control-plane feature (`06`).
- **Placement defaults** for a container with no shared-capability declaration come from the distribution feature; the type system only reports them. This is consistent with the constitution's default write acknowledgement of two replicas and the protocol drivers feature's clamping rule.
- **Composition write rules** are fixed per kind, not per definition (confirmed in Clarifications, Session 2026-09-13): `Union` and `Materialized View` are read-only, the latter changing only through refresh from its sources under a synchronous or asynchronous freshness policy; `Federated`, `Partitioned`, `Sharded`, `Replicated`, and `Distributed` route a write to the single member their key or placement rule selects. Multi-member atomicity is the L1 distributed transactions capability, not a composition feature. Missing-member tolerance and maximum nesting depth are documented per kind and are planning decisions.
- **Compositions are namespace-scoped**; cross-namespace composition is a possible future addition through the tenancy feature and is out of scope here.
- **Schema ownership**: the type system defines, stores, validates, and evolves each container's schema; drivers render it in their protocol's form but never keep one of their own (confirmed in Clarifications, Session 2026-09-13). Evolution is additive in place; incompatible changes are transforms. Which types are schema-required, schema-optional, or schema-free is recorded in the catalog. Value domains are FR-024a. The constitution's "each namespace MUST have schema and data inside it" is satisfied by the union of its containers' schemas; a namespace-level schema object beyond that belongs to the tenancy feature.
- **Changing L0 options after creation** (encoding, compression, key) applies forward; rewriting existing data is a transform of the migration and transforms feature (`10`), as is changing a container's type, an incompatible schema change, or a fixed shared-capability parameter.
- **Query planning behaviour** when a type lacks a native operation (fallback scan versus refusal to the client) is the query execution feature's decision (`05`); the type system guarantees an accurate, metadata-only answer about what the type can do.
- **Metric series names and labels** are owned by the observability feature (`08`); the type system guarantees the counts in FR-044 are tracked with type name and namespace. Per-type quotas and access policies are owned by the tenancy feature (`07`); the type system guarantees per-type resource accounting.
- **Catalog output form** (structured document format, CLI presentation) and the registration mechanism for new types (compile-time registry, plug-in manifest, or both) are planning decisions constrained by FR-045 through FR-049.
- **Conformance harness and starter documentation** for every type are deliverables of this feature, consistent with the constitution's documented-configuration principle.

## Out of Scope

The intent file assigns the following to sibling features. This specification does not define them; it only reserves the touchpoints listed.

- **Label, disk, memory, and region topology; replica placement; quorum semantics; sync/async replication; rebalancing and failure handling mechanics** (intent `04`). This feature carries shared-capability declarations and compatibility; what they do is defined there.
- **Query parser, planner, scheduler, executor, MapReduce, joins, aggregation, transactions** (intent `05`). This feature provides capability descriptors and the abstract type interface the planner consumes.
- **Controller hierarchy, Raft elections, and boot-time restore orchestration** (intent `06`). This feature guarantees each type can restore its own state and definition.
- **Per-namespace quotas, access policies, and role names** (intent `07`). This feature provides per-type accounting. Key unwrap, KMS, and audit are `14`.
- **WAL, fsync, tombstone/`gc_grace`, snapshot/PITR** (intent `13`) except that tombstone is a distinct value state in this catalog.
- **AuthN, permission vocabulary, master-key hierarchy** (intent `14`) except consuming key references.
- **Transforms between types and storage models, migration between nodes and namespaces, re-encoding and re-encryption of existing data, and incompatible schema changes that require rewriting data** (intent `10`). This feature owns schema definition and additive evolution, refuses in-place type changes and destructive schema changes, and points to that mechanism.
- **Metric series names per datatype** (intent `08`). This feature guarantees the counts exist with type name and namespace labels.
- **Data browsing UI across levels** (intent `09`). This feature guarantees the catalog and descriptions it would display.
- **Protocol-specific type mappings, carriers, and name escaping** (feature `002`). This feature provides the canonical representation and catalog those mappings are built on.
- **Cross-namespace compositions** and **user-defined types outside the registration path**; both are possible future additions through the expandable inventory.
- **Kafka as a stored log product** — product non-goal (`16`); Kafka is ingest (`09`) and outbound logging (`08`); Log Stream is the L3 type.
